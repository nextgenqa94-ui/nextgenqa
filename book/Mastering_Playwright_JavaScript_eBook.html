Chapter 01

Introduction to Automation Testing

1.1 What is Software Testing?

Software testing is the process of evaluating a system or application to find defects, ensure quality, and verify that it meets specified requirements. Testing is not just about finding bugs — it is about building confidence that software works as intended for end users.

1.2 Manual vs Automation Testing

Manual testing involves a human tester interacting with the software, following test cases, and documenting results. While effective for exploratory and usability testing, manual testing is slow, error-prone, and not scalable.

Automation testing uses scripts and tools to execute tests automatically, compare actual vs expected results, and generate reports — all without human intervention. It is faster, repeatable, and essential for Continuous Integration.

AspectManual TestingAutomation Testing
SpeedSlowFast
AccuracyHuman error possibleHighly accurate
Cost (long term)HighLow
ReusabilityNoneHigh
Best ForExploratory, UXRegression, Load, CI/CD

1.3 Types of Automation Testing

  • Unit Testing – Tests individual functions/components
  • Integration Testing – Tests interaction between modules
  • End-to-End (E2E) Testing – Tests complete user workflows
  • API Testing – Tests backend REST/GraphQL services
  • Performance Testing – Tests speed and scalability
  • Visual Regression Testing – Detects UI changes

1.4 The Testing Pyramid

The testing pyramid is a concept introduced by Mike Cohn. It recommends having more unit tests at the base, fewer integration tests in the middle, and even fewer E2E tests at the top.

/\
        /  \
       / E2E \        ← Few, Slow, Expensive
      /--------\
     / Integration\   ← Medium
    /--------------\
   /   Unit Tests   \  ← Many, Fast, Cheap
  /------------------\

1.5 Why Playwright for E2E Automation?

  • Supports Chromium, Firefox, and WebKit natively
  • Auto-wait built-in — no flaky sleeps needed
  • Supports JavaScript, TypeScript, Python, Java, C#
  • API testing built right into the framework
  • Network interception and mocking
  • Parallel execution out of the box
  • Codegen — record tests by clicking
  • Trace viewer — visual debugging tool
  • Backed by Microsoft, actively maintained

1.6 SDET Role in Modern Teams

A Software Development Engineer in Test (SDET) is responsible for building test infrastructure, automation frameworks, CI/CD pipelines, and ensuring quality is baked into the development process — not added as an afterthought. SDETs write production-quality code and collaborate closely with developers.

💡
Pro Tip

Pro Tip: As an SDET, focus on building reusable, maintainable frameworks — not just test scripts. Your code quality should match or exceed the application code quality.

1.7 Summary

  • Automation testing speeds up releases and improves reliability
  • The testing pyramid guides how many tests of each type to write
  • Playwright is the modern choice for E2E and API automation
  • SDETs own quality infrastructure, not just test scripts

Introduction to Playwright

2.1 What is Playwright?

Playwright is an open-source browser automation library developed by Microsoft. Released in 2020, it was built by the same team that created Puppeteer at Google. Playwright enables reliable end-to-end testing for modern web applications.

2.2 Playwright vs Other Tools

FeaturePlaywrightSeleniumCypress
Multi-browser✅ All 3 engines✅ WebDriver⚠️ Chrome/FF only
Auto-wait✅ Built-in❌ Manual waits✅ Built-in
API Testing✅ Native❌ No✅ Plugin
Network Mock✅ Yes❌ No✅ Yes
Parallel✅ Workers⚠️ Grid needed⚠️ Paid
Languages5 languagesManyJS/TS only
Mobile✅ Emulation✅ Appium⚠️ Limited

2.3 Key Playwright Concepts

  • Browser – Chromium, Firefox, or WebKit instance
  • BrowserContext – Isolated browser session (like incognito)
  • Page – Single browser tab or window
  • Locator – Smart element finder with auto-retry
  • Frame – iframe or child frame handle
  • Route – Network request interception
  • Trace – Recording of test execution for debugging

    { name: 'firefox',  use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit',   use: { ...devices['Desktop Safari'] } },
  ],
});

Chapter 04

Playwright Architecture & Internals

4.1 How Playwright Communicates with Browsers

Playwright communicates with browsers using low-level protocols: Chrome DevTools Protocol (CDP) for Chromium-based browsers, a custom protocol for Firefox, and WebKit's Remote Debugging Protocol for Safari. This gives Playwright deep control over browser behavior.

┌──────────────┐     WebSocket      ┌───────────────────┐
│  Playwright  │◄──────────────────►│  Browser Process  │
│  (Node.js)   │   CDP / Protocol   │  (Chromium/FF/WK) │
└──────────────┘                    └───────────────────┘

4.2 Browser, Context, and Page Hierarchy

Browser
 └── BrowserContext (isolated session — cookies, localStorage)
      ├── Page (tab 1)
      │    ├── Frame (main frame)
      │    └── Frame (iframe)
      └── Page (tab 2)

4.3 BrowserContext Deep Dive

BrowserContext is the most important concept in Playwright. Each context is completely isolated — separate cookies, localStorage, session storage, and cache. This allows you to simulate multiple users in the same test run.

const { chromium } = require('@playwright/test');

(async () => {
  const browser = await chromium.launch();

  // Context 1: Admin user
  const adminCtx = await browser.newContext({
    storageState: './auth/admin.json'
  });

  // Context 2: Regular user (completely isolated)
  const userCtx = await browser.newContext({
    storageState: './auth/user.json'
  });

  const adminPage = await adminCtx.newPage();
  const userPage  = await userCtx.newPage();

  // Both run independently in parallel
  await adminPage.goto('https://app.com/admin');
  await userPage.goto('https://app.com/dashboard');

  await browser.close();
})();

4.4 Auto-Waiting Mechanism

When you interact with an element, Playwright automatically waits for it to be: attached to the DOM, visible, stable (not animating), enabled, and editable (for input actions). This is called actionability.

  • click() – waits for visible + enabled + stable
  • fill() – waits for visible + enabled + editable
  • check() – waits for visible + enabled + checkable
  • selectOption() – waits for visible + enabled
  • expect(locator).toBeVisible() – assertion auto-retries

4.5 Playwright's Retry Architecture

// Playwright retries assertions automatically for up to 5 seconds
// No need for manual waits!

// ❌ Bad practice (manual sleep)
await page.waitForTimeout(3000);
await page.click('#submit-btn');

// ✅ Good practice (auto-wait)
await page.click('#submit-btn'); // Playwright handles the wait
await expect(page.locator('.success-msg')).toBeVisible();
💡
Pro Tip

Pro Tip: Never use page.waitForTimeout() in production tests. Playwright's auto-wait handles 99% of timing issues. If you need it, something is wrong with your test design.

4.6 Parallel Execution Model

// playwright.config.js
module.exports = defineConfig({
  workers: 4,          // 4 parallel workers
  fullyParallel: true, // Tests within a file run in parallel too

  // Each worker gets its own browser instance
  // Each test gets its own BrowserContext
  // Zero shared state between tests
});

4.7 Summary

  • Playwright uses CDP/WebSocket for deep browser control
  • BrowserContext provides complete isolation per user/session
  • Auto-waiting makes tests reliable without sleep() calls
  • Parallel execution is built-in with worker processes

Chapter 06

Locators – Advanced Strategies

6.1 What Are Locators?

Locators are the way Playwright finds elements on a page. Unlike Selenium's WebElement, Playwright Locators are lazy — they don't fetch the element until an action is performed. They also automatically retry when the element is not found or not in the right state.

6.2 Recommended Locators (Priority Order)

// 1. Role-based (BEST — matches user perspective)
page.getByRole('button', { name: 'Submit' });
page.getByRole('link', { name: 'Home' });
page.getByRole('textbox', { name: 'Email' });

// 2. Label-based
page.getByLabel('Password');

// 3. Placeholder-based
page.getByPlaceholder('Enter your email');

// 4. Text-based
page.getByText('Welcome back');
page.getByText('Sign In', { exact: true });

// 5. Alt text (for images)
page.getByAltText('Company logo');

// 6. Title attribute
page.getByTitle('Close dialog');

// 7. Test ID (for devs who add data-testid)
page.getByTestId('login-button');

6.3 CSS and XPath (When Needed)

// CSS Selectors
page.locator('input[type="email"]');
page.locator('.login-form input:first-child');
page.locator('#submit-btn');
page.locator('[data-cy="login-btn"]');

// XPath (use sparingly)
page.locator('//button[text()="Submit"]');
page.locator('xpath=//div[@class="modal"]//button');

// nth element
page.locator('.product-card').nth(2);  // 3rd card
page.locator('.product-card').first();
page.locator('.product-card').last();

6.4 Chaining and Filtering

// Filter by text within a parent
page.locator('.product-card')
    .filter({ hasText: 'Sauce Labs Backpack' });

// Filter by child element
page.locator('.product-card')
    .filter({ has: page.locator('.price', { hasText: '$29' }) });

// Chain locators
const form = page.locator('#login-form');
await form.getByLabel('Username').fill('admin');
await form.getByLabel('Password').fill('secret');
await form.getByRole('button', { name: 'Login' }).click();

6.5 Locator Assertions

const btn = page.getByRole('button', { name: 'Submit' });

await expect(btn).toBeVisible();
await expect(btn).toBeEnabled();
await expect(btn).toBeDisabled();
await expect(btn).toHaveText('Submit');
await expect(btn).toHaveAttribute('type', 'submit');
await expect(btn).toHaveClass(/primary/);
await expect(btn).toBeChecked();   // for checkboxes
await expect(btn).toHaveFocus();
💡
Pro Tip

Pro Tip: Always prefer getByRole() and getByLabel() over CSS/XPath. They are resilient to styling changes and reflect how users actually interact with the page — making tests more meaningful.

6.6 Common Mistakes

  • ❌ Using page.$ or page.$$ (old API) — use page.locator() instead
  • ❌ Hardcoding index-based selectors like nth(0) everywhere
  • ❌ Using XPath for everything — it's brittle
  • ❌ Not using filter() when multiple elements match
  • ✅ Use data-testid attributes for dynamic, complex elements

// Alert dialog
page.on('dialog', dialog => {
  console.log(dialog.message());
  dialog.accept();
});
await page.getByRole('button', { name: 'Show Alert' }).click();

// Confirm dialog — accept or dismiss
page.on('dialog', dialog => dialog.accept());
// OR
page.on('dialog', dialog => dialog.dismiss());

// Prompt dialog — fill text
page.on('dialog', async dialog => {
  await dialog.accept('John Doe'); // types text
});

// Get iframe by selector
const frame = page.frameLocator('#payment-frame');
await frame.getByLabel('Card Number').fill('4111111111111111');

await frame.getByRole('button', { name: 'Pay' }).click();

// Get frame by URL
const frame2 = page.frame({ url: /payment-provider.com/ });

// Nested iframes
const outerFrame = page.frameLocator('#outer');
const innerFrame = outerFrame.frameLocator('#inner');
await innerFrame.getByRole('button').click();

7.4 Mouse and Keyboard Actions

// Hover
await page.locator('.menu-item').hover();

// Double click
await page.locator('.editable-cell').dblclick();

// Right click
await page.locator('.item').click({ button: 'right' });

// Drag and Drop

// Keyboard shortcuts

7.5 Handling New Windows and Tabs

// Wait for new page (tab/window) to open
const [newPage] = await Promise.all([
  page.waitForEvent('popup'),
  page.getByRole('link', { name: 'Open in new tab' }).click(),
]);
await newPage.waitForLoadState();
await expect(newPage).toHaveTitle(/New Page/);
await newPage.close();
💡
Pro Tip

Pro Tip: Use frameLocator() instead of frame() when possible — it supports the full Locator API with auto-waiting. The old frame() API requires manual waits.

Chapter 08

Assertions & Validations

8.1 expect() – The Assertion Engine

Playwright's expect() function provides web-first assertions that automatically retry until the condition is met (up to the configured timeout). This is fundamentally different from Chai/Jest expect which checks only at that instant.

8.2 Page Assertions

// URL assertions
await expect(page).toHaveURL('https://app.com/dashboard');
await expect(page).toHaveURL(/dashboard/);

// Title assertions
await expect(page).toHaveTitle('Dashboard – MyApp');
await expect(page).toHaveTitle(/Dashboard/);

8.3 Locator Assertions

const el = page.locator('.message');

// Visibility
await expect(el).toBeVisible();
await expect(el).toBeHidden();

// Text content
await expect(el).toHaveText('Login successful');
await expect(el).toContainText('successful');
await expect(el).toHaveText(/success/i); // regex

// Attribute
await expect(el).toHaveAttribute('href', '/home');
await expect(el).toHaveAttribute('disabled');

// CSS Class
await expect(el).toHaveClass('active');
await expect(el).toHaveClass(/btn-primary/);

// Value (for inputs)
await expect(page.getByLabel('Name')).toHaveValue('Amir Khan');

// Count
await expect(page.locator('.item')).toHaveCount(5);

// State
await expect(page.getByRole('checkbox')).toBeChecked();
await expect(page.getByRole('button')).toBeEnabled();
await expect(page.getByRole('button')).toBeDisabled();
await expect(page.getByLabel('Email')).toBeFocused();

// Input value is empty
await expect(page.getByLabel('Search')).toBeEmpty();

8.4 Soft Assertions (Non-Blocking)

// Soft assertions — test continues even if assertion fails
// All failures collected and reported at end
test('product page checks', async ({ page }) => {
  await page.goto('/product/123');

  await expect.soft(page.locator('.title')).toHaveText('Product Name');
  await expect.soft(page.locator('.price')).toContainText('$');
  await expect.soft(page.locator('.add-cart')).toBeEnabled();
  // Test continues even if some assertions fail
});

8.5 Custom Expect Messages

await expect(page.locator('.error'), 
  'Error message should be visible after failed login'
).toBeVisible();

8.6 API Response Assertions

const response = await page.request.get('/api/users');

Page Object Model (POM)

18.1 What is POM?

The Page Object Model (POM) is a design pattern where each web page (or major component) is represented as a class. Locators and actions for that page live in the class. Tests use the page objects instead of directly interacting with the page. This makes tests readable and maintenance easy — when a locator changes, you fix it in one place.

18.2 Complete POM Implementation

// pages/InventoryPage.js
class InventoryPage {
  constructor(page) {
    this.page = page;
    this.productList = page.locator('.inventory_item');
    this.cartBadge   = page.locator('.shopping_cart_badge');
    this.cartLink    = page.locator('.shopping_cart_link');
    this.sortDropdown = page.locator('[data-test="product_sort_container"]');
  }

  async addProductToCart(productName) {
    await this.page
      .locator('.inventory_item')
      .filter({ hasText: productName })
      .getByRole('button', { name: /add to cart/i })
      .click();
  }

  async getCartCount() {
    const text = await this.cartBadge.textContent();
    return parseInt(text || '0');
  }

  async sortBy(option) {
    await this.sortDropdown.selectOption(option);
  }

  async goToCart() {
    await this.cartLink.click();
  }
}

module.exports = InventoryPage;

// Retry a specific action
async function retryAction(action, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    try {
      return await action();
    } catch (err) {
      if (i === maxRetries - 1) throw err;
      console.log(`Attempt ${i + 1} failed, retrying...`);
      await new Promise(r => setTimeout(r, 1000));
    }
  }
}

Chapter 24

Best Practices & Design Patterns

24.1 The Golden Rules of Playwright Testing

  • ✅ Use getByRole() first — it tests like a real user
  • ✅ Keep tests independent — each test sets its own state
  • ✅ Use fixtures for shared setup, not beforeEach
  • ✅ Use API for test data setup, not UI
  • ✅ Name tests descriptively: 'user can add product to cart' not 'test1'
  • ✅ One assertion per test concept — not one test per file
  • ❌ Never use page.waitForTimeout()
  • ❌ Never hardcode credentials in test files
  • ❌ Never use test.only in committed code
  • ❌ Never share state between tests via module-level variables

24.2 AAA Pattern – Arrange, Act, Assert

test('user can update profile email', async ({ page }) => {
  // ARRANGE — set up preconditions
  await page.goto('/profile');
  await expect(page.getByLabel('Email')).toHaveValue('old@email.com');

  // ACT — perform the action being tested
  await page.getByLabel('Email').fill('new@email.com');
  await page.getByRole('button', { name: 'Save Changes' }).click();

  // ASSERT — verify the expected outcome
  await expect(page.locator('.success-toast')).toHaveText('Profile updated!');
  await expect(page.getByLabel('Email')).toHaveValue('new@email.com');
});

24.3 DRY vs DAMP

Tests should be DAMP (Descriptive And Meaningful Phrases), not DRY (Don't Repeat Yourself). Some repetition in tests is acceptable if it makes them more readable. Over-abstracting tests makes them hard to understand.

24.4 Test Naming Conventions

// Good naming — describes behavior
test('login fails with invalid password');
test('cart shows 0 items for new user');
test('admin can delete any user');
test('checkout requires valid credit card');

// Bad naming — meaningless
test('test1');
test('check login');
test('verify cart');

// qa-agent/agent.js
const Anthropic = require('@anthropic-ai/sdk');
const { execSync } = require('child_process');
const fs = require('fs');

const client = new Anthropic();

// Tools the agent can use
const tools = [
  {
    name: 'generate_test',
    description: 'Generate a Playwright test for a requirement',
    input_schema: {
      type: 'object',
      properties: {
        requirement: { type: 'string', description: 'Test requirement' },
        pageName:    { type: 'string', description: 'Page to test' },
      },
      required: ['requirement']
    }
  },
  {
    name: 'run_test',
    description: 'Execute a Playwright test file',
    input_schema: {
      type: 'object',
      properties: {
        filePath: { type: 'string', description: 'Path to test file' },
      },
      required: ['filePath']
    }
  },
  {
    name: 'save_file',
    description: 'Save content to a file',
    input_schema: {
      type: 'object',
      properties: {
        path:    { type: 'string' },
        content: { type: 'string' },
      },
      required: ['path', 'content']
    }
  }
];

// Tool execution
function executeTool(toolName, toolInput) {
  switch(toolName) {
    case 'save_file':
      fs.writeFileSync(toolInput.path, toolInput.content);
      return `File saved: ${toolInput.path}`;
    
    case 'run_test':
      try {
        const result = execSync(
          `npx playwright test ${toolInput.filePath} --reporter=list`,
          { encoding: 'utf8', timeout: 120000 }
        );
        return result;
      } catch(e) {
        return `Test failed: ${e.stdout}${e.stderr}`;
      }
    
    default:
      return 'Unknown tool';
  }
}

// Agentic loop
async function runQAAgent(userStory) {
  const messages = [{
    role: 'user',
    content: `You are an expert SDET. Given this user story, 
    generate a Playwright test, save it, run it, and report results.
    
    User Story: ${userStory}`
  }];

  while (true) {
    const response = await client.messages.create({
      model: 'claude-opus-4-20250514',
      max_tokens: 4096,
      tools,
      messages
    });

    messages.push({ role: 'assistant', content: response.content });

    if (response.stop_reason === 'end_turn') {
      const text = response.content.find(b => b.type === 'text');
      console.log('Agent Result:', text?.text);
      break;
    }

    if (response.stop_reason === 'tool_use') {
      const toolResults = [];
      for (const block of response.content) {
        if (block.type === 'tool_use') {
          const result = executeTool(block.name, block.input);
          toolResults.push({
            type: 'tool_result',
            tool_use_id: block.id,
            content: result
          });
        }
      }
      messages.push({ role: 'user', content: toolResults });
    }
  }
}

Q1: What is the difference between page.locator() and page.$() in Playwright?

// page.$() — returns ElementHandle (old API, deprecated)
// - Fetches element immediately, may be stale

Q4: What is the difference between BrowserContext and Browser?

  • Browser: the actual browser process (Chromium/FF/WebKit)
  • BrowserContext: isolated session within a browser — own cookies, localStorage, cache
  • Multiple contexts in one browser = multiple independent sessions
  • Each test should get its own BrowserContext (Playwright does this automatically)
