API + UI Integration — Why, When & Value

The foundational thinking that separates senior SDETs from junior ones
01
🏢Why Real Companies Use API + UI Integration
Concept
Pure UI automation is slow, brittle, and expensive. Pure API testing misses rendering bugs. Hybrid testing uses each layer for what it does best — API for data setup/teardown, UI for visual & interaction verification.
Usage
At Freecharge/Axis Bank: recharge flows create transactions via API, then UI validates correct display on wallet dashboard. Saves 3–5 UI login steps per test run. A 200-test suite runs 40% faster vs pure UI approach.
Mistake
Using UI to create every piece of test data (clicking through 6 screens to create one user). This inflates test runtime and creates cascading failures when the creation UI breaks.
Interview
"API tests are 10-100x faster than UI. We use API for state setup and teardown, UI only for the specific user journey being tested. This keeps tests fast, reliable, and focused."
⚖️When to Prefer API over UI
Concept
Decision rule: If the user never sees it in the current test scenario, use API. Setup, teardown, data seeding, authentication, cleanup — always API. Only use UI for what you're explicitly testing.
Code 
// ❌ BAD — UI to set up data for a different test goal
test('validate order total on checkout', async ({ page }) => {
  await page.goto('/login');
  await page.fill('#email', 'user@test.com');
  await page.fill('#pass', 'secret');
  await page.click('#login-btn');          // 3 unnecessary UI steps
  await page.goto('/products');
  await page.click('.product-card:first-child');  // 4 more steps
  await page.click('#add-to-cart');
  // ... total: 10+ steps before the REAL test even starts
});

// ✅ GOOD — API setup, UI for what matters
test('validate order total on checkout', async ({ page, request, authedPage }) => {
  const order = await createOrderViaAPI(request, { items: [{ sku: 'P001', qty: 2 }] });
  await authedPage.goto(`/orders/${order.id}`);  // jump straight to goal
  await expect(authedPage.locator('.order-total')).toHaveText(`₹${order.total}`);
});
Interview
"The test pyramid says: many unit tests, fewer integration, even fewer E2E. Hybrid API+UI is the 'smart E2E' layer — full browser validation without the full browser setup cost."

Playwright Fixtures — Deep Implementation

page · request · custom fixtures · cross-layer data sharing
02
🧩page & request Fixtures — What They Really Are
Concept
page = Playwright Page instance with its own browser context. request = APIRequestContext with baseURL from config. Both are test-scoped by default — fresh per test, auto-disposed.
Code 
// Built-in fixtures — both available in same test
import { test, expect } from '@playwright/test';

test('use both in one test', async ({ page, request }) => {
  // request — pure HTTP, no browser
  const res  = await request.post('/api/users', { data: payload });
  const user = await res.json();

  // page — browser, inherits baseURL from config for navigation
  await page.goto(`/users/${user.id}`);
  await expect(page.locator('h1')).toHaveText(user.name);
});

// KEY: request fixture uses baseURL from playwright.config
// KEY: page fixture is a fresh browser tab per test
// KEY: they share NO session — separate contexts by default
Mistake
Assuming page and request share cookies/sessions — they don't. The request fixture is a separate HTTP context, not linked to the browser's cookie jar.
🔧Custom Fixture — The Power Pattern
Concept
test.extend() lets you define reusable fixtures that compose multiple concerns: auth, services, pre-seeded data. Tests import your test object, not Playwright's base one.
Code 
// src/fixtures/base.fixture.js
import { test as base, expect } from '@playwright/test';
import { UserService   } from '../api/UserService.js';
import { OrderService  } from '../api/OrderService.js';
import { LoginPage     } from '../pages/LoginPage.js';
import { getAuthState  } from '../helpers/auth.helper.js';

export const test = base.extend({

  // API service fixtures
  userService:  async ({ request }, use) => await use(new UserService(request)),
  orderService: async ({ request }, use) => await use(new OrderService(request)),

  // Pre-authenticated browser page
  authedPage: async ({ browser }, use) => {
    const ctx  = await browser.newContext({
      storageState: await getAuthState()  // inject saved session
    });
    const pg   = await ctx.newPage();
    await use(pg);
    await ctx.close();                     // always cleanup
  },

  // Pre-seeded user — create via API, pass to test
  seededUser: async ({ userService }, use) => {
    const user = await userService.createAndParse(buildUser());
    await use(user);                        // test runs
    await userService.remove(user.id);     // auto cleanup
  },
});

export { expect };
Usage
Tests that import from base.fixture.js get all these as named params. No boilerplate per test file. The seededUser fixture auto-creates and auto-deletes the user around each test.
Interview
"Fixtures in Playwright work like dependency injection. The use() function is the yield point — code before use() runs before the test, code after runs as teardown. This is how we get zero-boilerplate cleanup."

Authentication Optimization

Login via API · token generation · storageState · inject into browser
04
⚡Login via API — storageState Injection
Concept
Instead of filling login form on every test, call the auth API once in globalSetup, save cookies + localStorage to auth.json, then inject that state into every browser context. UI tests start already logged in.
Code 
// src/global/globalSetup.js
import { request } from '@playwright/test';
import { config } from '../config/env.config.js';
import fs from 'fs/promises';

export default async function globalSetup() {
  const ctx = await request.newContext({ baseURL: config.baseUrl });

  // Option A — Form-based login (sets session cookie)
  await ctx.post('/auth/login', {
    form: { email: process.env.TEST_EMAIL, password: process.env.TEST_PASS }
  });
  await ctx.storageState({ path: './auth-state/user.json' });

  // Option B — JWT login (save token for API, cookie for UI)
  const res   = await ctx.post('/auth/jwt/login', {
    data: { email: process.env.ADMIN_EMAIL, password: process.env.ADMIN_PASS }
  });
  const { access_token, refresh_token } = await res.json();
  process.env.ACCESS_TOKEN = access_token;
  await fs.writeFile('./auth-state/tokens.json',
    JSON.stringify({ access_token, refresh_token })
  );
  await ctx.dispose();
}

// playwright.config.js
export default defineConfig({
  use: {
    storageState: './auth-state/user.json'  // applied to ALL page fixtures
  },
  globalSetup: './src/global/globalSetup.js',
});
Usage
Every test's page fixture now opens the browser already authenticated. Zero login steps in test code. For multi-role testing (admin vs user), create separate auth-state/admin.json and auth-state/user.json.
Mistake
Committing auth-state/*.json to git — contains live session tokens. Add to .gitignore. Regenerate in CI via globalSetup. Also: not refreshing tokens when they expire (run time > token lifetime).
Interview
"storageState captures cookies, localStorage, and sessionStorage into a JSON file. When loaded into a browser context, the browser behaves as if the user already completed login — even SSO flows with complex redirect chains."
🎭Multi-Role Auth & Token Injection Patterns
Code 
// src/helpers/auth.helper.js — multi-role manager
import { request } from '@playwright/test';
import { config } from '../config/env.config.js';
import path from 'path';
import fs from 'fs/promises';

const ROLES = {
  admin:   { email: process.env.ADMIN_EMAIL,  pass: process.env.ADMIN_PASS  },
  user:    { email: process.env.USER_EMAIL,   pass: process.env.USER_PASS   },
  viewer:  { email: process.env.VIEWER_EMAIL, pass: process.env.VIEWER_PASS },
};

export async function setupAuthState(role = 'user') {
  const statePath = path.join('./auth-state', `${role}.json`);
  const creds     = ROLES[role];
  const ctx       = await request.newContext({ baseURL: config.baseUrl });
  await ctx.post('/auth/login', { data: creds });
  await ctx.storageState({ path: statePath });
  await ctx.dispose();
  return statePath;
}

// Inject JWT into localStorage for SPA apps
export async function injectToken(page, token) {
  await page.addInitScript(({ token }) => {
    window.localStorage.setItem('access_token', token);
    window.localStorage.setItem('auth_state', 'authenticated');
  }, { token });
}

// Fixture — admin-authenticated page
adminPage: async ({ browser }, use) => {
  const statePath = await setupAuthState('admin');
  const ctx = await browser.newContext({ storageState: statePath });
  await use(await ctx.newPage());
  await ctx.close();
},
Interview
"page.addInitScript() runs before any page script — ideal for injecting tokens into localStorage before the SPA boots. The SPA reads localStorage on init and considers itself authenticated."

🔄 Cross-Layer Validation — Complete Strategy
// Cross-validation: API data → UI display → back to API
test('dashboard stats match API source of truth', async ({ request, authedPage }) => {
  // Step 1: Fetch ground truth from API
  const apiRes  = await request.get('/api/dashboard/stats');
  expect(apiRes).toBeOK();
  const apiData = await apiRes.json();

  // Step 2: Navigate UI and extract displayed values
  await authedPage.goto('/dashboard');
  await authedPage.waitForSelector('[data-testid="stats-loaded"]'); // wait for async load

  const uiTotalUsers  = await authedPage.locator('[data-testid="total-users"]').textContent();
  const uiTotalOrders = await authedPage.locator('[data-testid="total-orders"]').textContent();

  // Step 3: Cross-validate (parse UI text to number)
  expect(parseInt(uiTotalUsers, 10)).toBe(apiData.totalUsers);
  expect(parseInt(uiTotalOrders, 10)).toBe(apiData.totalOrders);
});

// Validate UI table rows match API list
test('user list UI matches API data', async ({ request, authedPage }) => {
  const res   = await request.get('/api/users?page=1&limit=10');
  const { data: users } = await res.json();

  await authedPage.goto('/admin/users');
  const rows = authedPage.locator('[data-testid="user-row"]');
  await expect(rows).toHaveCount(users.length);

  // Validate each row's email matches API
  for (let i = 0; i < users.length; i++) {
    await expect(rows.nth(i).locator('.email')).toHaveText(users[i].email);
  }
});

// After UI action — verify via API (reverse cross-validation)
test('UI delete → verify gone via API', async ({ request, authedPage, seededUser }) => {
  await authedPage.goto(`/admin/users/${seededUser.id}`);
  await authedPage.click('[data-testid="delete-btn"]');
  await authedPage.click('[data-testid="confirm-delete"]');
  await expect(authedPage.locator('.success-toast')).toBeVisible();

  // Cross-validate — API should return 404 now
  const apiCheck = await request.get(`/api/users/${seededUser.id}`);
  expect(apiCheck.status()).toBe(404); // API confirms deletion
});
💡 Strategy: API is the source of truth. UI must reflect it. Always validate both directions: API creates → UI shows it, UI deletes → API confirms it's gone.

Network Interception — Advanced

page.route() · mock responses · modify dynamically · block calls
07
🕸️page.route() — Core Patterns
Concept
page.route(pattern, handler) intercepts network calls before they leave the browser. Handlers can: fulfill (return mock), continue (pass-through), abort (block), or modify the real response.
Code 
// 1. FULFILL — return mock response (no server call)
await page.route('**/api/users**', async route => {
  await route.fulfill({
    status:      200,
    contentType: 'application/json',
    body:        JSON.stringify({ data: [{ id: 'u1', name: 'Mock User' }] })
  });
});

// 2. ABORT — block analytics / ads / 3rd-party trackers
await page.route(/google-analytics|hotjar|intercom/, r => r.abort());

// 3. MODIFY — intercept real response and alter fields
await page.route('**/api/feature-flags', async route => {
  const res  = await route.fetch();           // get real response
  const body = await res.json();
  body.newCheckoutEnabled = true;              // inject feature flag
  await route.fulfill({ response: res, body: JSON.stringify(body) });
});

// 4. CONDITIONAL — mock only POST, pass through GET
await page.route('**/api/payments', async route => {
  if (route.request().method() === 'POST') {
    await route.fulfill({
      status: 200,
      body:   JSON.stringify({ txnId: 'MOCK-TXN-001', status: 'SUCCESS' })
    });
  } else {
    await route.continue();                  // let GET pass through
  }
});
Usage
Use abort to kill slow trackers (saves 200–500ms/test). Use fulfill to test error states (500, 401) without breaking the real backend. Use modify to enable unreleased feature flags.
Mistake
Not removing routes after a test — page.route() is cumulative in the same context. Use page.unroute() or scope routes inside tests with fresh page per test.
📡Capture & Assert Network Requests

Synchronization — Critical Patterns

API + UI sync · event-based waits · eliminating flakiness
08
⏳API → UI Propagation Delays
Concept
After creating data via API, UI may not immediately show it — cache TTL, SSE lag, polling intervals, React re-renders. Never use page.waitForTimeout(2000). Always use event-based waits.
Code 
// ❌ NEVER — flaky hard wait
await page.waitForTimeout(2000);  // time bomb

// ✅ Wait for element with retry-safe assertion
await expect(page.locator('[data-testid="new-user-row"]'))
  .toBeVisible({ timeout: 8000 });  // Playwright polls until visible

// ✅ Wait for specific network response after API creates data
const [listResponse] = await Promise.all([
  page.waitForResponse('**/api/users?**'),  // UI refetches the list
  page.click('[data-testid="refresh-btn"]'),
]);
expect(listResponse.status()).toBe(200);

// ✅ Poll API until resource is ready (async processing)
async function waitForJobCompletion(request, jobId, maxMs = 30000) {
  const deadline = Date.now() + maxMs;
  while (Date.now() < deadline) {
    const res = await request.get(`/api/jobs/${jobId}`);
    const job = await res.json();
    if (job.status === 'completed') return job;
    if (job.status === 'failed')    throw new Error(`Job failed: ${job.error}`);
    await new Promise(r => setTimeout(r, 500));  // poll every 500ms
  }
  throw new Error(`Job ${jobId} did not complete in ${maxMs}ms`);
}

// ✅ Wait for URL change after login redirect
await page.waitForURL(/\/dashboard/, { timeout: 10000 });

// ✅ waitForLoadState — choose the right one
await page.waitForLoadState('networkidle');  // ← for pages with many XHR calls
await page.waitForLoadState('domcontentloaded'); // ← for SPAs
Mistake
Using networkidle everywhere — it waits for zero network activity for 500ms. On live chat or analytics-heavy pages, it never fires. Use targeted waitForResponse or element visibility instead.
Interview
"Flakiness from hard waits is test debt. Every waitForTimeout is a future incident. Playwright's auto-waiting on locator assertions (toBeVisible, toHaveText) handles most cases — the key is trusting the framework."
🔁Sync Anti-Patterns & Fixes
Code 
// ANTI-PATTERN 1: Race condition — UI navigates before API response processed
// ❌ BAD
await request.post('/api/orders', { data: payload });
await authedPage.goto('/orders');  // may load before order is in DB!
expect(authedPage.locator('.order-row')).toHaveCount(1); // FLAKY

// ✅ GOOD — await full API response before navigating
const res   = await request.post('/api/orders', { data: payload });
const order = await res.json();  // confirms write completed
await authedPage.goto(`/orders/${order.id}`); // navigate to specific resource

// ANTI-PATTERN 2: Parallel API + UI without Promise.all
// ❌ BAD — sequential when it could be parallel
await request.get('/api/orders');
await authedPage.goto('/orders');

// ✅ GOOD — fire both at the same time
const [apiRes] = await Promise.all([
  request.get('/api/orders'),
  authedPage.goto('/orders'),
]);

// ANTI-PATTERN 3: Forgetting Playwright auto-waits
// ❌ BAD — manually waiting before Playwright already does
await page.waitForSelector('.submit-btn');  // redundant
await page.click('.submit-btn');           // click already waits

// ✅ GOOD
await page.click('.submit-btn');  // auto-waits for visible+enabled

// src/api/UserService.js
import { buildUser } from '../factories';
import { expect } from '@playwright/test';

export class UserService {
  constructor(request) {
    this.request = request;
    this.base    = '/api/v2/users';
  }

  async getAll(params = {}) {
    return this.request.get(this.base, { params });
  }

  async getById(id) {
    return this.request.get(`${this.base}/${id}`);
  }

  async getByEmail(email) {
    const res  = await this.request.get(this.base, {
      params: { email, limit: 1 }
    });
    const { data } = await res.json();
    return data[0] ?? null;
  }

  async create(data) {
    return this.request.post(this.base, { data });
  }

  async createAndParse(data = {}) {
    const payload = { ...buildUser(), ...data };
    const res     = await this.create(payload);
    expect(res.status(), 'User creation failed').toBe(201);
    return res.json();
  }

  async update(id, data) {
    return this.request.patch(`${this.base}/${id}`, { data });
  }

  async remove(id) {
    const res = await this.request.delete(`${this.base}/${id}`);
    if (![204, 404].includes(res.status())) {
      console.warn(`⚠ Cleanup: failed to delete user ${id}`);
    }
  }

  async promoteToAdmin(id) {
    const res = await this.request.post(`${this.base}/${id}/promote`);
    expect(res).toBeOK();
    return res.json();
  }
}

Best Practices

Test isolation · anti-flakiness · maintainable architecture
12
🧪

Tests Must Be Self-Contained

Every test creates its own data, validates it, and deletes it. Never depend on data from another test. Use afterEach cleanup tracking arrays.

🔀

API for Setup, UI for Verification

If it's not what the test is testing, do it via API. The test goal determines which layer handles which step.

🔐

One storageState per Role

Create admin.json, user.json, viewer.json in globalSetup. Never hardcode credentials in test files — use env vars + fixtures.

🎯

Use data-testid Selectors

Never use CSS classes or XPath for production test selectors. data-testid survives redesigns. Make it a frontend team requirement.

⚡

Promise.all for Parallel API Calls

When creating multiple independent resources in setup, use Promise.all() — 3x–5x faster than sequential awaits.

🚫

Zero Hard Waits

Ban waitForTimeout from your codebase. Use Playwright's built-in auto-waits, waitForResponse, waitForURL, or element visibility assertions.

🏭

Factory Functions for All Test Data

buildUser(overrides) with faker-generated defaults. Overrides only what the test cares about. Zero hardcoded test data.

📦

Service Layer = 1-File Endpoint Changes

When an API endpoint changes, update UserService.js — not 50 test files. This is the #1 maintainability win at scale.

📊

test.step() for Readable Reports

Wrap logical sections in await test.step('...', async () => {}). HTML reporter shows nested steps — team can debug without reading code.

🏷️

Tag Every Test

@smoke, @critical, @regression tags in test titles. CI runs --grep @smoke on PR, full suite nightly. Selective execution = faster feedback.

🔒

Security Test Layer Built-in

Test: no token → 401, wrong role → 403, other user's data → 403/404, expired token → 401. These come free with hybrid testing.

🧠

API as Test Oracle

After every UI write action (create, delete, update), cross-validate via API. API is the source of truth — UI is just a presentation layer.
